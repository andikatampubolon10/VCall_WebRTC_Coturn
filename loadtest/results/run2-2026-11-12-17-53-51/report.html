Rekomendasi

  • Hentikan broadcastUserList() ke semua client pada setiap register/call/accept/hangup (biaya O(N²)); kirim hanya perubahan (delta) atau hanya ke pihak terkait.
  • Ganti fs.appendFileSync di setiap log dengan logger asinkron (mis. stream/pino) atau matikan log per-pesan di produksi.
  • Jalankan gateway dalam mode cluster PM2 (mis. 4 instance) dengan sticky session atau broker (Redis pub/sub) agar memakai semua core.
  • CoTURN berjalan dengan opsi verbose dan menulis log ke file; di produksi matikan verbose agar CPU dan disk tidak terbebani log per-paket/per-alokasi.
  • Untuk angka kapasitas murni CoTURN, ulangi uji dengan load generator di VM terpisah dalam region yang sama (opsi --monitor ssh).

2. Skenario Stress Test Virtual User (VU)

Apa itu Virtual User (VU)?

Satu VU adalah satu pengguna aplikasi yang disimulasikan secara penuh oleh program uji, bukan sekadar request HTTP. Setiap VU memiliki:

  • koneksi WebSocket sendiri ke signaling gateway (seperti browser yang membuka aplikasi),
  • socket UDP dan alokasi relay TURN sendiri di CoTURN (seperti ICE agent WebRTC),
  • aliran media dua arah ±572 kbps per arah (audio Opus + video) yang benar-benar diteruskan oleh CoTURN.

VU selalu berpasangan: User A (dokter, APP_A) yang menekan tombol panggil dan User B (pasien, APP_B) yang menerima. Jadi N VU = N/2 video call yang berlangsung bersamaan.

Siklus hidup satu pasangan VU

  1. Masuk aplikasi — A & B connect WebSocket + register.
  2. Panggil — A call → B incoming → B accept.
  3. Siapkan jalur media — A & B TURN Allocate, tukar offer/answer + kandidat relay, CreatePermission + ChannelBind.
  4. Bicara — media video/audio mengalir dua arah lewat CoTURN selama sisa ramp-up + seluruh jendela pengukuran.
  5. Tutup — A hangup, kedua VU melepas relay (Refresh lifetime 0) dan menutup koneksi.

Pola beban: step-load (tangga) sampai titik jenuh

  • Bertahap: rencana 100 → 200 → 300 → 350 → 400 → 450 → 500 → 600 VU; dijalankan sampai 350 VU. Tiap tahap dimulai dari nol agar hasil antar tahap tidak saling memengaruhi.
  • Ramp-up: panggilan dimulai merata sepanjang durasi ramp (kolom laju kedatangan = VU baru per detik), meniru pengguna yang masuk tidak serentak.
  • Tahan (hold): setelah semua panggilan tersambung, beban ditahan 90 detik. Semua metrik kualitas dan sumber daya server di laporan ini diambil dari jendela ini (kondisi stabil/steady-state).
  • Hangup & cooldown 30 detik, menunggu CoTURN melepas semua port relay sebelum tahap berikutnya.
  • Dua penilaian per tahap: Server (panggilan tersambung, kualitas media, CPU, RAM) menentukan kapasitas dan titik jenuh server; Signaling (waktu setup panggilan, CPU gateway) menilai gateway aplikasi secara terpisah.
  • Kapasitas server = tahap tertinggi sebelum kriteria Server pertama kali dilanggar.
  • VU dijalankan oleh beberapa proses worker paralel di server yang sama (CPU generator dipisahkan dari penilaian); total durasi pengujian 9 menit.

6. Metodologi & Kriteria

Skenario per pasangan panggilan

Setiap tahap membuat N/2 pasangan. User A (aplikasi dokter) memanggil User B (aplikasi pasien) dengan protokol yang sama seperti aplikasi asli:

  1. A dan B membuka WebSocket ke gateway lalu mengirim register.
  2. A mengirim call (mode video), B menerima incoming lalu mengirim accept.
  3. A dan B masing-masing melakukan TURN Allocate ke CoTURN (tantangan 401 → kredensial long-term, RFC 5766).
  4. Pertukaran SDP offer/answer dan ICE candidate bertipe relay lewat gateway.
  5. A dan B melakukan CreatePermission + ChannelBind ke alamat relay lawan.
  6. Media dua arah mengalir sebagai ChannelData: A → CoTURN → relay A → relay B → CoTURN → B (dan sebaliknya).
  7. Setelah jendela pengukuran: A mengirim hangup, keduanya melepas alokasi (Refresh lifetime 0).

Panggilan dihitung berhasil hanya jika media benar-benar diterima di kedua arah melalui relay CoTURN.

Profil beban & tahapan

  • Profil media: paket setiap 20 ms — audio 172 B + video 1250 B ≈ 572 kbps dan 100 paket/detik per arah per user.
  • Tahapan: 100 → 200 → 300 → 350 user (rencana: 100, 200, 300, 350, 400, 450, 500, 600).
  • Setiap tahap: ramp-up bertahap (panggilan dimulai merata), lalu 90 detik jendela pengukuran dengan semua panggilan aktif, kemudian teardown dan cooldown 30 detik sampai port relay CoTURN kembali dilepas.
  • Pengujian otomatis berhenti pada tahap pertama yang melanggar SLA (breaking point).
  • Telemetri server dicatat setiap 1 detik oleh agen di server (/proc): CPU per core & per proses, RAM, jaringan, statistik UDP kernel, port relay, file descriptor.
  • Latensi one-way dan jitter diukur dari timestamp di setiap paket; pengirim dan penerima berada di proses yang sama sehingga jamnya identik.
